# merge-honours-gpgsign-and-repository-hooks  [high]  fix_accepted=False

## Summary
TRUE AS STATED, and broader than stated: the integration merge inherits `commit.gpgsign` and every commit-stage repository hook, so a `prepare-commit-msg` hook silently replaces the message of an authoritative merge commit and a `commit-msg` hook or a signing failure blocks the integration while being reported as a merge conflict — and the same inheritance reaches the control repository, where a global `commit.gpgsign = true` makes `project init` fail outright.

## Root cause
src/git/integration_worktree.rs:125-128 —
    let output = run(&scope, ["merge", "--no-ff", "--no-edit", "-m", message, commit]);
No `-c commit.gpgsign=false`, no `-c core.hooksPath=...`, no `--no-verify`. The invocation runs with whatever `commit.gpgsign`, `gpg.*`, and `.git/hooks/*` the candidate repository and the operator's `~/.gitconfig` supply.

src/git/command.rs:139-159 (`AMBIENT_OVERRIDES`) and 175-186 (`run`) are the layer that already neutralises the environment — it strips GIT_DIR, GIT_CONFIG_*, and the identity variables for exactly this class of reason (defect 16) — but it neutralises only *environment variables*. Configuration reaching git through `~/.gitconfig` and `.git/config`, and behaviour reaching it through `.git/hooks`, is untouched. `GIT_CONFIG_GLOBAL` is removed from the child env, which suppresses one delivery route for the operator's global config while leaving the default `$HOME/.gitconfig` route wide open.

src/control/repository.rs:168 (`git init`, no `-c init.templateDir=`) and :308 (`run_ok(&self.scope(), ["commit", "-q", "-m", message])`, no signing or hook neutralisation) extend the same omission to the audit trail.

src/commands/integration.rs:2493 (`["merge", "--ff-only", landing_sha]`) runs the project's `post-merge` hook against the protected worktree during promotion (probe3.sh section E: `POST-MERGE ran, squash=0, HEAD=10d1c08`). It cannot block — probe5.sh section J: a `post-merge` exiting 1 still leaves `merge exit=0` — but it can dirty the tree.

The failure classification is at src/git/integration_worktree.rs:129-134: every non-zero exit becomes `ErrorCode::ConflictMergeFailed` with the text "did not apply", so signing failures and hook refusals are indistinguishable from content conflicts.

Unaffected, and the implementer should not touch them: `merge-tree` (src/git/merge.rs:155) and `commit-tree` (src/git/integration_worktree.rs:186, src/git/landing.rs:118) neither sign nor run hooks — verified, probe2.sh B and B2.

## Files
src/git/integration_worktree.rs, src/git/command.rs, src/control/repository.rs, src/error.rs, tests/support/mod.rs, tests/merge_preflight.rs

## Proposed fix
Principle to hold: an object the *harness* authors must not be alterable or blockable by project configuration; a working tree the harness *materialises* must still get the project's checkout automation. Those are different invocations and must be treated differently.

A. HARNESS-AUTHORED COMMITS — neutralise per invocation, never by writing config.
Add to src/git/command.rs a documented constant beside AMBIENT_OVERRIDES and a way for a call site to request it (e.g. `run_neutral(&scope, args)` / a `Neutrality` argument), which injects `-c` flags after the scope prefix and before the subcommand. `git -C <path> -c k=v <subcommand>` is verified working, including in a linked worktree (probe5.sh section N).
  - `commit.gpgsign=false` and `tag.gpgsign=false`. Verified: probe4.sh section I, `-c commit.gpgsign=false` overrides a repo-local `commit.gpgsign=true` — merge exit 0, `git cat-file commit HEAD | grep -c gpgsig` = 0.
  - `core.hooksPath=<absolute path guaranteed not to hold hooks>`, e.g. `<scope path>/.git/change-harness-no-hooks`. Verified: probe5.sh H (nonexistent dir: exit 0, empty stderr, message preserved, no hooks ran) and H2 (existing empty dir: same). The path must be absolute — a relative `core.hooksPath` is resolved against the working-tree top and is ambiguous here.
  - Do NOT rely on `--no-verify` alone. Verified insufficient: probe4.sh section G — with `--no-verify`, `pre-merge-commit` and `commit-msg` were skipped but `prepare-commit-msg` still ran and the resulting commit's subject was `HIJACKED`. Git offers no flag that suppresses `prepare-commit-msg`.
Apply to: src/git/integration_worktree.rs:125-128 (the integration merge); src/control/repository.rs:308 (the control commit — a global `prepare-commit-msg` would otherwise rewrite audit-trail messages); src/control/repository.rs:168, which additionally needs `-c init.templateDir=` (probe4.sh L: without it a global template installs a `pre-commit` into the control repo and blocks its first commit; with it, zero template hooks are copied).

B. VERIFY THE OBJECT, DO NOT TRUST THE FLAGS. In `integration_worktree::merge`, after the merge, read the created commit and refuse unless: its message equals the message passed in; it carries no `gpgsig` header (`git cat-file commit <head>`); it has exactly two parents, the second being `commit`. This is what makes the test non-vacuous — it fails if a future Git changes hook semantics, whereas asserting "we passed the flag" only restates the implementation.

C. STOP CALLING AN ENVIRONMENT REFUSAL A CONFLICT. On non-zero exit, branch on `git ls-files -u` in the worktree (probe5.sh K2/K3/K4: conflict → 3 unmerged entries; hook refusal → 0; gpg failure → 0; exit status alone cannot separate them). Non-empty ⇒ keep `ErrorCode::ConflictMergeFailed`. Empty ⇒ a new code, e.g. `PreconditionGitEnvironment` / `CH-PRECONDITION-GIT-ENVIRONMENT` in the Precondition category, whose remediation names `commit.gpgsign`, `core.hooksPath` and the repository's hooks — never "run integration preflight", which reports clean (probe: `preflight clean = true` while the merge dies). Adding a code means updating `ErrorCode::ALL` (currently `[Self; 78]`, src/error.rs:200) and the exhaustive matches at src/error.rs:357, :441, :704.

D. PROMOTION. Give src/commands/integration.rs:2493 the same neutrality for consistency, or state at the call site why `post-merge` is left to run there. Either is defensible; silence is not.

FAILING-FIRST TESTS (each must fail against today's code; the observed failure is given):
 1. `an_integration_merge_ignores_a_prepare_commit_msg_hook` — hook writes "chore: message chosen by the hook"; assert the commit subject is exactly "integrate F-001 into INT-001". Today: subject is the hook's. MUTATION: drop `-c core.hooksPath=...` ⇒ fails at the message assertion, not elsewhere.
 2. `a_commit_msg_hook_cannot_block_an_integration` — `commit-msg` exits 1; assert merge succeeds and HEAD moved. Today: Err(CH-CONFLICT-MERGE-FAILED).
 3. `an_integration_merge_is_not_signed_however_the_operator_configured_git` — TWO fixtures, both required. (a) `commit.gpgsign=true` + `gpg.program=/nonexistent/gpg`: today exit 128. (b) `commit.gpgsign=true` with a *working* signer — `gpg.format=ssh`, `user.signingkey=<ssh-keygen ed25519 .pub>` (probe3.sh D proves this signs on this host with no keyring): assert the merge succeeds AND `git cat-file commit HEAD` has no `gpgsig` line. Without (b), a fix that merely swallowed signing errors would pass (a).
 4. `the_control_repository_commits_under_an_operators_signing_configuration` — spawn the binary the way tests/support/mod.rs:162 does, with `.env("HOME", fake)` where `fake/.gitconfig` sets `commit.gpgsign = true` and `gpg.program`; run `project init`; assert success and a control commit exists. TRAP TO AVOID, verified: delivering the same config via `.env("GIT_CONFIG_GLOBAL", ...)` makes the test pass vacuously — probe9.sh shows `project init` succeeding, because `AMBIENT_OVERRIDES` strips that variable. Also set `XDG_CONFIG_HOME`. tests/cli.rs:393 is the existing precedent for env-injection tests.
 5. `a_hook_refusal_is_not_reported_as_a_merge_conflict` — build the two index states by driving git directly (bypassing the harness's neutrality), then assert the classifier from (C) returns the environment code for the clean-index/MERGE_HEAD state and the conflict code for the unmerged state.

## Over-correction risk
Three distinct opposite failures, each needing its own guard.

1. NEUTRALISING TOO WIDE — killing the project's checkout automation. The tempting one-line "fix" is to add the `-c` flags inside `git::command::run` for every invocation. That also disables hooks on `git worktree add` (src/git/integration_worktree.rs:55-65) and on the promotion fast-forward, i.e. `post-checkout`/`post-merge` — precisely the hooks git-lfs and similar tools install to materialise a working tree. Smoke gates (src/commands/integration.rs:1186-1216) then run against a tree the project's own tooling never finished preparing, and the integration's verdict is about the wrong bytes. GUARD TEST: `worktree_creation_still_runs_the_projects_checkout_hooks` — install a `post-checkout` hook writing a marker file, call `integration_worktree::create`, assert the marker exists. This test fails the moment someone moves the neutrality into `run` unconditionally, which is exactly the mistake to hold open.

2. SWALLOWING REAL CONFLICTS. A fix that reclassifies every merge failure as "the environment refused" would turn genuine content conflicts into a precondition error and destroy the conflict reporting the product exists for. GUARD TESTS: `a_conflicting_merge_reports_a_conflict_and_can_be_aborted` (src/git/integration_worktree.rs:368) must be strengthened — its only assertion today is `error.to_string().contains("did not apply")` (line 383), a string a gpg failure and a hook refusal both produce, so it passes against the broken code and would pass against an over-aggressive fix too. It must assert `error.code()` is `ConflictMergeFailed` and that `git ls-files -u` was non-empty. `a_textual_conflict_blocks_the_merge_without_landing_anything` (tests/merge_preflight.rs:178-193) must keep asserting exit 6 / `CH-CONFLICT-MERGE-FAILED` after the new code exists.

3. "FIXING" THE OPERATOR'S MACHINE. Writing `git config commit.gpgsign false` into the candidate repository, or `core.hooksPath` into `.git/config`, would silently disable signing and hooks for the developer's own commits — a far worse outcome than the defect. GUARD TEST: `neutrality_is_per_invocation_and_never_written_to_the_project` — set `commit.gpgsign=true` locally, run a full integration merge, then assert `git -C <repo> config --local --get commit.gpgsign` still reports `true` and `git config --local --get core.hooksPath` is still unset, and that `.git/hooks/*` are byte-identical before and after.

Also worth stating so nobody widens the change on speculation: `merge-tree` and `commit-tree` are already unaffected (verified, exit 0 under `commit.gpgsign=true` with a broken gpg program), and `post-merge` cannot block anything (verified: a `post-merge` exiting 1 still leaves `git merge` at exit 0). None of the three needs neutralising, and touching them adds risk with no defect behind it.

Finally, a scope honesty note for the register: this is not a security fix. R-001/D-006 already accept that anyone who can write `.git/hooks` shares the OS account and could edit the objects directly. What is being repaired is that ordinary, sanctioned local configuration — the `commit.gpgsign = true` that GitHub's own documentation tells developers to set — currently alters an authoritative object without the harness noticing, or stops the harness dead while blaming a conflict that does not exist.

## VERIFIER objections
THE DEFECT REPRODUCES. I wrote my own probes (not the investigator's) against `change_harness::git::integration_worktree` and the real binary, git 2.50.1 (Apple Git-155). Every claim reproduced:
- `prepare-commit-msg` hook: `merge(&wt, cand, "integrate F-001 into INT-001")` returns Ok and the commit subject is "chore: message chosen by the hook".
- `commit-msg` exit 1 → Err(CH-CONFLICT-MERGE-FAILED) "did not apply: commit-msg: subject must reference a ticket".
- repo-local `commit.gpgsign=true` + broken `gpg.program` → Err(CH-CONFLICT-MERGE-FAILED), "gpg failed to sign the data".
- `post-merge` residue → `is_clean` false.
- `ls-files -u`: 3 entries for a real conflict, 0 for a hook refusal.
- Real binary, fake HOME with `commit.gpgsign=true`: `project init` → CH-EXTERNAL-GIT-COMMAND, exit 8, control history unborn. Fake HOME with global `core.hooksPath` refusing `pre-commit`: same. And the vacuity trap is real — the same config delivered via `GIT_CONFIG_GLOBAL` makes `project init` succeed, because AMBIENT_OVERRIDES strips it.
Severity is if anything understated: `landing::create` (src/commands/integration.rs:1650) makes the integration merge head the landing commit's SECOND PARENT, so the hook-rewritten message and the operator's signature are reachable from what promotion pushes. They land in authoritative history permanently, not in a disposable worktree. The investigator never says this.

THE FIX IS PARTLY RIGHT AND PARTLY WRONG. I applied part A at the merge site (`-c core.hooksPath=<abs> -c commit.gpgsign=false`) and ran the whole suite: 381 unit + all 29 integration binaries pass, 0 failures. So the core neutrality breaks nothing. I then verified both proposed tests and both stated mutations (see below). But four things are wrong:

1. `merge.log` IS NOT NEUTRALISED, AND PROPOSED CHECK (B) WOULD REFUSE EVERY INTEGRATION ON A REPO THAT SETS IT. Verified with the fix applied: with `merge.log = true` the commit body is "integrate F-001 into INT-001\n\n* commit '8f6ae14...':\n  feat: a". Check B says "refuse unless its message equals the message passed in" — that is a hard refusal of every integration on any repository with `merge.log=true`, an ordinary sanctioned local config exactly like the `commit.gpgsign` the finding defends. This is the "check that refuses everything" failure mode the repair sequence has already been bitten by three times. The `-c` list must include `merge.log=false` (and B must compare after that), or B must compare only the subject.

2. `merge.verifySignatures` IS NOT NEUTRALISED AND STILL BLOCKS. Verified with the fix applied: `merge.verifySignatures=true` → Err "did not apply: fatal: Commit 8f6ae14 does not have a GPG signature." Exit 128, zero unmerged entries. So under proposed classifier (C) it becomes the new environment code whose remediation names `commit.gpgsign`, `core.hooksPath` and "the repository's hooks" — none of which is the cause. The operator is sent looking in the wrong place. The finding's enumeration of config routes is incomplete; it stopped at the two it happened to probe.

3. THE `ls-files -u` DISCRIMINATOR SEPARATES CONFLICTS FROM *EVERYTHING ELSE*, NOT FROM "ENVIRONMENT REFUSALS". Verified: a merge refused because an untracked working-tree file would be overwritten gives exit 2, 0 unmerged entries, and NO MERGE_HEAD. That is neither a content conflict nor a signing/hook problem, and (C) would label it a Git-environment precondition and hand the operator gpgsign/hooksPath advice. It is reachable: `run_smoke_gates` (src/commands/integration.rs:1186-1216) runs inside the integration worktree *between* merges, so a gate that drops a build artifact can produce exactly this state on the next merge. The investigator's probe5 tested three states and generalised from three.

4. THE FIX CREATES, AT THE MERGE SITE, THE EXACT HARM ITS OWN OVERCORRECTION SECTION FORBIDS. `core.hooksPath` is all-or-nothing: suppressing `prepare-commit-msg`/`commit-msg` also suppresses `post-merge`. I confirmed this — my post-merge-residue probe went from "residue present" to "no residue" the moment the fix landed. The finding's overcorrection section says blanket neutrality is wrong because it kills "precisely the hooks git-lfs and similar tools install to materialise a working tree", so that "smoke gates then run against a tree the project's own tooling never finished preparing, and the integration's verdict is about the wrong bytes". `post-merge` is that class of hook, the integration worktree is the tree, and the smoke gates are those gates. The finding names the harm and then produces it at the one site where the gates actually run, without arguing the point. Either the merge must be split (merge, then run the project's post-merge deliberately; or `--no-commit` + a harness-authored commit object) or the trade must be stated and accepted at the call site. Silence here is the same omission the finding rightly complains about for promotion.

WHAT IS SOUND: the `-c` flag mechanism, verified working in a linked worktree; `-c commit.gpgsign=false` overrides a repo-local true and produces a commit with zero `gpgsig` lines; `--no-verify` alone is insufficient (subject became HIJACKED); `commit-tree` and `merge-tree` are genuinely unaffected under a broken gpg (both exit 0) so leaving them alone is right; `post-merge` exiting 1 leaves `merge --ff-only` at exit 0 so it cannot block promotion; the "don't write config into the project" principle; and the two failing-first tests I wrote to the spec both fail at the assertion that matters under the stated mutations — dropping `-c core.hooksPath` fails at `left: "chore: message chosen by the hook"` vs the harness message, and dropping `-c commit.gpgsign=false` fails at the `gpgsig` assertion with a real SSH signature in the object (ssh-keygen signing works on this host with no keyring, so test 3(b) is writable and non-vacuous).

NOT DELIBERATE. Invariant 7.1.6 ("Hooks are advisory and never count as integration evidence") is, read literally, about hooks not being *evidence*, not about hooks being *inert* — so the "contradicts an invariant" framing is weaker than stated, and D-006/R-001/D-013 mean this is not a security fix (the finding concedes this). But the register itself already lists "Merge honours commit.gpgsign and repository hooks" as an OPEN Tier 4 defect, so the project has adopted that reading, and the `project init`-fails-outright case needs no invariant at all to be a defect.

## VERIFIER missed
1. THIS IS NOT A NEW FINDING. docs/DEFECT-REGISTER.md line 91, Tier 4, already records "Merge honours `commit.gpgsign` and repository hooks, contradicting 'hooks are advisory'" as open and unfixed. The investigator never cites it and writes as if discovering it. The genuinely new material is the control-repository extension (`project init` fails outright) and the classification complaint.

2. `merge.log` and `merge.verifySignatures` — two further config routes that alter or block the harness-authored merge and survive the proposed fix (both verified above). A fix that enumerates config routes must enumerate them.

3. The blast radius: the integration merge commit is the landing commit's second parent (src/commands/integration.rs:1650-1655), so it reaches the protected branch. The investigator argues severity from the worktree, which is the weaker case; the real case is permanent authoritative history.

4. `run_smoke_gates` runs between merges inside the integration worktree, which is both why suppressing `post-merge` there is dangerous (objection 4) and why the untracked-file merge failure is reachable (objection 3). The investigator treats the integration worktree as a place where only merges happen.

5. Unexamined interaction with defect 17's `head == before` guard: it also returns ConflictMergeFailed and would, under classifier (C), be re-examined by `ls-files -u` — that path exits 0 with a clean index, so a naive implementation of (C) that classifies on index state alone would relabel "candidate already contained" as a Git-environment problem. The classifier must run only on the non-zero-exit branch, which the proposal implies but never says.

6. Nothing was said about `core.hooksPath` needing to point somewhere the *candidate repo owner cannot create* — the proposal puts it at `<scope path>/.git/change-harness-no-hooks`, inside a directory the project controls. Harmless under D-013, but it undercuts the "not alterable by project configuration" principle the fix is built on, and deserves a sentence.

7. No check of whether `backup`/`archive`/`authority` production paths create commits. I grepped: they do not — only integration_worktree::merge, integration.rs:2493, control/repository.rs:168 and :308, plus commit-tree sites. The finding's site list is complete; it just never shows the search that establishes it.
